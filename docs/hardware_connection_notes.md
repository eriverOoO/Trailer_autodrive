# 실차 USB 연결 확인과 G6 미해결 사항

2026-11-06 작업 기록입니다. 당시 연결 확인 결과이며 현재 포트 번호나 센서의 기계적 정상 상태를 보장하지 않습니다.

## 연결 및 확인 결과

```text
PC USB 1개 → 전원 공급형 USB 허브 → G6 / Arduino Mega / IMU
Jackery AC 출력 → 멀티탭 → USB 허브 전원 어댑터
```

이 구성은 Jackery의 **AC 출력**을 사용합니다. 배터리 USB 단자에서 직접 전원을 받는 구성이라면
해당 모델의 USB 또는 DC/USB 출력 버튼을 사용합니다.
참고: [Jackery 공식 출력 제어 설명](https://r.jackery.net/productGuide/Jackery%20Explorer%201000%20v2%20User%20Manual-new.pdf).

| 당시 포트 | 확인한 내용 |
|---|---|
| `/dev/ttyUSB0` | YDLIDAR G6 장치 정보 및 원시 거리 패킷 수신 |
| `/dev/ttyUSB1` | IMU 숫자 프레임 801개/8.01초, 약 100Hz 수신 |
| `/dev/ttyACM0` | Arduino Mega 2560 USB 인식 및 접근 권한 |

차량 모터 명령 송신, 아두이노 펌웨어 읽기/업로드, 실제 차량 주행은 수행하지 않았습니다.
USB 인식은 저장소 펌웨어가 실제 보드에 올라가 있다는 증거가 아닙니다.
IMU 값의 방향·단위·보정 정확도도 별도 확인 대상입니다.

## 시리얼 권한과 장치 식별

처음에는 계정에 `dialout` 그룹 권한이 없어 접근이 거부됐습니다.
임시 ACL을 적용했지만 재연결하면서 초기화되어 이 PC에는 CP2102와 해당 Arduino를 위한 udev 소유권 규칙을 적용했습니다.
이 시스템 설정은 Git 푸시만으로 다른 PC에 설치되지 않습니다.
새 PC에서는 보통 계정을 `dialout`에 추가한 뒤 다시 로그인하고 개발 도구도 새로 시작해 권한을 확인합니다.

```bash
sudo usermod -aG dialout "$USER"
# 로그아웃 후 다시 로그인
id
ls -l /dev/ttyUSB* /dev/ttyACM*
```

포트 번호는 재연결 순서에 따라 바뀔 수 있습니다.
당시 G6와 IMU의 CP2102가 같은 USB serial 번호 `0001`을 사용해 `/dev/serial/by-id` 링크가 중복됐습니다.
두 장치를 같은 센서로 간주하지 말고 `/dev/serial/by-path`와 실제 연결 위치를 함께 확인해야 합니다.

## 허브 오류와 라이다 단독 시험

IMU가 연결돼 있던 허브 포트에서 `disabled by hub (EMI?), re-enabling...`와 USB 연결 해제가 반복됐습니다.
이 문구만으로 전원 부족·간섭·케이블·포트 중 하나를 원인으로 확정하지 않았습니다.
라이다만 남겨 시험한 뒤 다른 허브 위치에 IMU와 아두이노를 재연결했습니다.
재연결 후 관찰 구간에는 라이다 패킷 수신과 IMU 연속 수신이 유지됐고 새 USB 끊김 로그가 없었습니다.
허브 전체가 영구적으로 정상이라는 검증은 아닙니다.

## G6 식별 및 비정상 회전 보고

기존 코드의 RPLIDAR 설정으로 시도한 뒤, 수신한 모델 번호 13·펌웨어 3.2·하드웨어 3으로 **YDLIDAR G6**를 식별했습니다.
공식 G6 기본 속도는 512000bps지만 이번 연결에서는 115200bps에서 응답했습니다.
차이가 생긴 원인은 확인되지 않았으므로 다른 G6에 115200bps를 일반화하지 않습니다.
참고: [YDLIDAR 공식 모델별 설정](https://github.com/YDLIDAR/ydlidar_ros2_driver/blob/master/details.md).

`tools/g6_lidar_diagnostic.py`는 원시 패킷 식별·체크섬 진단 도구입니다.
ROS LaserScan이나 차량 제어용으로 보정한 각도를 발행하지 않으며 자동 시작 서비스나 주차 launch에도 포함되지 않습니다.

체크섬 오류 없이 거리 데이터가 수신됐고 사용자가 회전 자체를 확인했지만,
이후 **회전 상태가 정상적이지 않다**고 알려 라이다를 분리했습니다. 진단 프로세스도 종료됐습니다.
결론은 **데이터 수신 확인 / 기계적인 정상 회전 미검증 및 이상 보고**입니다.
패킷이 나온다는 이유로 정상 회전이나 고장 복구 완료로 기록하면 안 됩니다.

health 응답에서는 문서화된 0/1/2 외의 값 **60**도 관찰됐습니다.
그 의미는 미확인이며, 최신 진단 도구는 이 값이면 스캔 시작을 거부합니다.
장치 분리 후 정지 전송/DTR 설정이 실패해도 포트 닫기를 시도하도록 했습니다.
원인 확인 전에는 다시 회전시키는 시험을 재개하지 않은 상태입니다.

[주차 명령 저장·재생 기능](parking_command_replay.md)은 이 진단 도구와 독립적이며 저장한 공간 정보로 CPU 계획을 수행합니다.
