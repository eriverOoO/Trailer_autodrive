# 주차 프로젝트 참고자료 검토

검토일: 2026-11-16. 논문의 주장과 아래 **프로젝트 적용 제안**을 구분했습니다.
논문 알고리즘을 이번 작업에서 제어·인식 코드에 적용하거나 실차로 검증하지 않았습니다.
GPU 시뮬레이터도 실행하지 않았습니다. 사용자가 자료를 보고 도입 여부를 결정합니다.

## 검토 범위와 현재 구현

루트 README의 참고자료와 현재 실차 워크스페이스의 모델·계획·제어·센서 코드를 대조했습니다.
루트 `src/trailer_parking_pkg`의 명령 재생과 `mvsim_slam_real`의 실시간 인식·계획은 실행 경로가 다릅니다.
논문을 인용했다는 이유로 논문의 전체 알고리즘이 구현되었다고 보지 않았습니다.

현재 실차 경로는 전륜 조향 견인차+수동 트레일러의 off-axle 모델, 4차원 Hybrid A*,
LQR 기반 추종과 보호 어댑터입니다. 어댑터의 조향 출력은 -7~7 단계이고,
이동 요청의 모터 출력은 현재 고정 ±50 PWM입니다. 속도 비례 제어가 아닙니다.
실차 치수·장착 위치·조향 부호와 응답은 논문의 차량 수치를 대신할 수 없습니다.

카메라·LiDAR는 시각 차이 0.10 s 이내의 자료를 대응시키고, 구조물 확인 근거를 odom에 저장합니다.
현재 문서상 카메라 대응 경로에는 스캔 중 움직임 보정이 없습니다.
공간 확정의 연속 관측 검사는 있지만 통계적 불확실성 추정과는 다릅니다.
계획 실패 중에도 공간 인식을 갱신하는 기능은 이미 있으므로 새 제안으로 세지 않았습니다.

## 추가로 검토할 만한 내용

### 1. 카메라와 2D LiDAR 외부 보정 — 인식 쪽 우선 후보

**논문:** Fan 등, 2019, [Extrinsic Calibration between a Camera and a 2D Laser Rangefinder using a Photogrammetric Control Field](https://www.mdpi.com/1424-8220/19/9/2030).

**내용:** 좌표를 알고 있는 기준점들과 방 모서리를 공통 기준으로 사용해 두 센서의 자세를 각각 구하고,
센서 사이 회전·이동을 계산합니다. 3D LiDAR가 아니라 2D 거리 센서를 직접 다루는 점이 맞습니다.
논문의 단일 촬영 방식에는 미리 측정한 control field가 필요합니다.

**프로젝트 적용 제안:** 현재 보정 JSON을 넣는 절차에 별도 검증 영상을 추가합니다.
실제 왼쪽 구조물을 여러 거리·각도에서 보며 투영된 LiDAR 점이 영상 윤곽과 얼마나 맞는지 기록하고,
보정에 사용하지 않은 장면으로 오차를 평가합니다. 정확히 논문 방식을 재현할지,
별도의 다자세 보드 보정을 택할지는 설치 공간에 따라 결정합니다.

**판단 포인트:** 센서 높이가 달라 같은 물체의 서로 다른 단면을 보는 문제와
가림은 외부 보정만으로 해결되지 않습니다. 도입 효과는 투영 오차와 잘못된 구조물 대응 비율로 확인합니다.
연결 위치는 `real_parking/two_structure_test.py`의 카메라·LiDAR 대응과 기존 보정 파일 처리입니다.

### 2. 인식 오차를 고려한 주차 계획 — 공간이 흔들리는 경우

**논문:** Lee·Lim·Sunwoo, 2020, [Robust Parking Path Planning with Error-Adaptive Sampling under Perception Uncertainty](https://www.mdpi.com/1424-8220/20/12/3560).

**내용:** 검출한 주차공간의 위치·방향에 오차가 있다는 전제로 가능한 경로 후보를 생성하고,
효용을 평가해 경로를 고릅니다. 정확한 목표 하나만 가정하는 계획보다 인식 불확실성을 직접 다룹니다.

**프로젝트 적용 제안:** 동일 공간에 ID를 붙여 중심·방향의 관측 분산과 확인 횟수를 저장합니다.
목표 자세가 조금씩 움직일 때 매번 다른 공간으로 확정하지 않고, 변화가 충분히 클 때
정지 상태에서 다시 계획하는 방식을 검토할 수 있습니다. 통계적 공간 추적과 전환 억제는
논문에서 착안한 우리 시스템용 제안이며 논문 구현의 단순 복사는 아닙니다.

**판단 포인트:** 트레일러에 대한 성능 근거로 바로 사용할 수 없습니다. 관측이 틀렸는데 확신만 커지는
상황도 평가해야 합니다. 기존 0.18 m 최소 차체 여유를 줄이는 근거로 쓰지 않고,
필요하면 불확실성 때문에 추가 여유를 요구합니다. 적용 후보는 `two_structure_gap.py`와 목표 확정 단계입니다.

### 3. 추정 가능한 상태를 고려하는 제어 — 후진 접힘 관리

**논문:** Ljungqvist 등, 2020, [Estimation-aware model predictive path-following control for a general 2-trailer with a car-like tractor](https://arxiv.org/abs/2002.10291).

**내용:** 후진 시 불안정한 연결각을 제어하면서, 센서 시야 때문에 정확히 추정할 수 있는
연결각 범위도 MPC 제약에 반영합니다. 이진 변수를 쓰는 방식과 더 보수적인 연속 제약 방식을 비교합니다.

**프로젝트 적용 제안:** 우리 장비는 두 IMU를 쓰므로 논문의 시야 제약을 그대로 붙이지 않습니다.
대신 IMU 지연·바이어스·연결각 신뢰도가 나빠지는 조건에서 후진을 허용할지,
추정이 좋은 자세로 전진 보정할지를 계획·제어에 반영하는 아이디어를 검토할 수 있습니다.

**판단 포인트:** 논문은 트레일러 두 대이고 우리는 한 대입니다. 모델과 제약을 다시 구성해야 하며,
현재 LQR·상태 감시를 대체하려면 명확한 개선 근거가 필요합니다. 조향 단계·지연·고정 PWM 특성을
먼저 측정해야 MPC가 예측하는 입력과 실제 입력이 일치합니다. 관련 코드는 `estimator.py`,
`yaw_estimator.py`, `vendor/tractor_parking_controller.py`, `adapter.py`입니다.

### 4. 경로를 조향하기 쉬운 궤적으로 다듬기 — 계획 성공 이후의 후보

**논문/코드:** [Tracailer, 2025 v2](https://arxiv.org/html/2502.19832v2)·[공식 저장소](https://github.com/Tracailer/Tracailer).

**내용:** 탐색으로 얻은 초기값에서 견인차·트레일러의 운동학과 충돌 제약을 고려해
부드러운 궤적과 시간을 함께 최적화합니다. 검색 성공 여부뿐 아니라 추종하기 쉬운 궤적을 다룹니다.

**프로젝트 적용 제안:** 기존 Hybrid A* 결과를 유지한 채 후처리 후보로 비교하고,
차량 전체의 충돌·연결각 검사를 다시 통과한 결과만 채택하는 구성을 검토할 수 있습니다.

**판단 포인트:** 공식 예제는 ROS 1/catkin이며 MPC는 CasADi와 qpOASES 설정을 요구합니다.
현재 ROS 2 환경에 바로 붙일 수 없습니다. 특히 확인한 MPC의 `stateTrans`는
우리 모델의 뒤 차축-히치 오프셋 항과 동일하지 않고, 최적화 예외를 무시하는 코드도 있어
실차 제어에 그대로 복사하면 안 됩니다. BSD-3-Clause 고지도 확인 대상입니다.
CPU에서의 계산 시간은 우리 PC에서 별도 측정해야 하며 이 문서는 GPU 시뮬레이션 성능을 주장하지 않습니다.

### 5. 스캔 중 차량 움직임 보정 — 논문 외 실용 코드

**공식 코드:** ROS [laser_geometry](https://github.com/ros-perception/laser_geometry), BSD-3-Clause.

**내용/제안:** 점별 획득 시각과 TF를 사용한 LaserScan 변환을 참고해,
전진 중 촬영한 영상에 스캔 전체를 한 시각으로 겹칠 때 생기는 오차를 줄일 수 있습니다.
LiDAR 드라이버가 제공하는 `stamp`, `time_increment`와 이동 추정이 먼저 정확해야 합니다.

**판단 포인트:** 현재 `lidar.py`는 시각 순서가 있는 스캔의 단순 반전을 거부합니다.
`time_increment`를 0으로 만들어 검사를 피하면 보정에 필요한 정보가 사라집니다.
Cartographer 내부 처리와 카메라 대응 경로를 따로 확인해 중복 보정을 피해야 합니다.
설치 검토 시 현재 ROS Humble에 맞는 버전을 선택해야 합니다.

## 도입 여부를 판단하기 좋은 순서 — 프로젝트 코드에서 내린 제안

1. 보정과 센서 시간 품질: 정지/손으로 전진한 기록에서 투영 오차, 오대응률, 공간 위치 흔들림 비교.
2. 실차 입력 모델: 조향 단계별 실제 각도·응답 시간, ±50 PWM의 전후진 속도·정지 거리 측정.
   이 항목은 특정 논문의 성능 주장이 아니라 현재 어댑터 구현 때문에 필요한 사전 작업입니다.
3. 인식 불확실성: 같은 공간 ID 유지율, 잘못된 확정률, 계획 실패와 무관한 인식 갱신 여부 비교.
4. 궤적 최적화/MPC: 위 자료가 갖춰진 뒤 동일 기록과 동일 초기 상태에서 기존 방식과 비교.
   계획 성공률, 최소 전체 차체 여유, 최대 연결각, 조향 변화, 최종 자세 오차, CPU 지연을 평가.

처음 세 항목의 기록·재생 비교에는 GPU 시뮬레이터가 필요하지 않습니다.
실제 주차 성능과 센서 없는 시간 명령 재생의 반복성은 별도로 검증해야 합니다.
논문에서 잘 된 경로라도 초기 자세·바닥·배터리 상태가 달라지면 개방 루프 명령 재생 결과는 달라집니다.

C++ 이식 검토는 이미 [이슈 #1](https://github.com/eriverOoO/Trailer_autodrive/issues/1)에 있습니다.
논문 구현 언어만으로 현재 병목이나 실차 성능 개선을 단정하지 않습니다.
